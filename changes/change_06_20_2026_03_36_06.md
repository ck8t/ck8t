### Technical Details

**3-process debug paths:**
```
client.js breakpoint → in-browser BlockDebugEngine (existing, unchanged)
extension.js breakpoint → WS to extension bridge → BlockDebugEngineNode (vm.Script) → HTTP /ck8t/run-block hold-open
server.js breakpoint → "Test on Server" button → WS to ck8t-server → BlockDebugEngineNode (vm.Script)
```

**WS debug protocol:**
- Client sends: `register {sessionId}` or `start {sessionId, blockType, breakpoints, ctxValues, ...}`
- Server pushes: `paused {file, line, variables, callStack}`, `resumed`, `completed {output}`, `error {message}`, `log {level, msg}`
- Client sends (during session): `resume`, `stepOver`, `stepInto`, `stepOut`, `stop`

**Extension.js ordering contract:**
`startExtDebugSession()` resolves only after WS open + `register` sent. Browser then issues HTTP POST. `waitForRegisteredSocket()` on server side polls until socket registered before creating engine.

**CJS preprocessor:**
`module.exports = [` → `const __ck8tRunners = [` so community block CJS format works in `vm.Script` context.

**URL separation:**
- `__CK8T_BRIDGE_BASE__` → extension bridge (`debug-ws` on bridge)
- `VITE_CONVENGINE_BASE` / `:3001` → ck8t-server (`debug-ws` on server)
- Never swap these.
